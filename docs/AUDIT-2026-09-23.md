# PEM prototype audit, 23 September 2026

Full audit of the charts and of every interactive control, run three ways:

1. **Prototype diff.** The v1.0 single-file HTML prototype and the React build
   were rendered side by side and compared programmatically across 3 lenses x 4
   periods: every hero tile, every metric section's text, and for every chart the
   bar count, bar geometry, axis ticks, area path, hover-target count and
   viewBox. 231 differences on the first pass.
2. **Live product.** `enhance.prohance.io/phpemwebui/vendorPerformance` was
   opened and its Highcharts options read directly off the React fibre tree, so
   the comparison is against the real chart configuration rather than a
   screenshot.
3. **Interaction sweep.** Every control driven in a real browser on all three
   lenses and the vendor drilldown.

Everything below is fixed in 1.1.0 unless marked otherwise.

---

## Charts

### 1. Columns rendered 7px tall (blocker)

The single most visible defect, and the one in the reported screenshot. The
prototype's stylesheet carries `.bar { height: 7px }` for the progress bars under
Capacity Utilization and Headcount by Role. The React `ColumnChart` put
`className="bar"` on its SVG `<rect>` elements to hang a transition off. In SVG 2
the CSS geometry properties apply to `<rect>` and **beat the presentation
attribute**, so every column collapsed to 7px while its `height` attribute still
read the correct value. Automated geometry checks reading the attribute could not
see it.

Fixed: the chart class is now `.col-bar`. A Playwright test measures rendered
`getBBox().height` rather than the attribute, so a future collision fails the build.

### 2. Paired columns were grouped, the product overlays them

Read from the live chart options:

```
plotOptions.column: { grouping: false, groupPadding: 0.1, borderRadius: 4, borderWidth: 0 }
series[0] target tasks     color #D1D5DB  pointPadding 0.05  zIndex 0
series[1] completed tasks  color #2563EB  pointPadding 0.28  zIndex 1
yAxis: { min: 0, endOnTick: true }
```

`grouping: false` places both series on the same category rather than side by
side, so the chart reads as one wide grey bar with a narrower blue bar centred on
top. Same pattern for Total deliveries against On-time deliveries. The prototype
and the first React build both drew them side by side.

Fixed: `ColumnChart` defaults to `layout="overlay"` with the product's paddings.
Widths follow Highcharts: slot minus `groupPadding` on each side gives the group,
then each series is trimmed by its own `pointPadding`. A `maxPointWidth` of 40px
stops a three-day view turning into slabs; it never bites at the nine-month or
thirteen-week views, so those stay pixel-identical. `layout="grouped"` is still
available if a future chart wants it.

Corners are top-only rounded, drawn as a path, because a rect with `rx` rounds
the base as well.

### 3. Axis maxima were wrong on every chart

The rounding ladder had lost four rungs. The product lands on
`1, 1.5, 2, 2.5, 3, 4, 5, 7.5, 10`; the port had `1, 2, 2.5, 5, 10`. Every bar
height and every area path was therefore scaled wrong, typically by 0.8.

Fixed, and pinned by `npm run test:charts`, which runs in a second with no
browser.

### 4. Vendor Score trend axis

Was floored at 50 and rounded to a multiple of ten. The product runs the axis
from 0 to a nice maximum above the data: 100 for a vendor scoring 88, 80 for one
scoring 65, 50 for one scoring 49.8. Now matched.

Residual, not fixed: Highcharts picks 80 where this ladder picks 75 for a data
maximum of 65. Chasing Highcharts' exact tick algorithm is not worth the
complexity; the difference is one gridline label on one vendor.

### 5. Sparklines

Were 108x44 with a flat fill. The product's are 120x44 with a 0.35 to 0 gradient,
a 1.5px stroke and `preserveAspectRatio="none"`, and the y range fits the data
rather than starting at zero. Now matched.

### 6. X-axis caption

Three metrics (Leakage Summary, Productive vs Non-Productive, Utilization of
High-rate Resources) carried a hardcoded "Day" caption in the v1.0 prototype,
even when the axis showed months. The React build derives it from the labels.
**This is a prototype defect the React build already fixed**; it is recorded here
so the difference is not mistaken for a regression.

## Filters

### 7. Both Reset and Apply pairs appeared dead

Reported directly, and confirmed. The cause was the commit-on-click model
introduced earlier at your request: because every change applied the instant it
was clicked, Apply had nothing left to do and Reset changed nothing visible when
everything was already selected. The popover also stayed open after Reset.

Fixed, with a model that keeps instant feedback where you asked for it and gives
both pairs real work:

| Control | Behaviour |
| --- | --- |
| Period tabs, date pickers, metric chips | commit on click, unchanged |
| Multiselect checkbox | stages a change, page does not move yet |
| Popover **Apply** | commits the staged selection, closes. Disabled when staged matches applied |
| Popover **Reset** | selects everything, commits, closes. Disabled when everything is already selected |
| Page **Apply** | commits whatever is staged in the open popover. Disabled when nothing is staged |
| Page **Reset** | restores every control on the page to its default. Disabled when already at defaults |

Disabled buttons are visibly greyed with a tooltip saying why, so a click that
would do nothing is now unavailable rather than silently ignored. The same model
is applied to the location filter on the vendor detail page, which gained a
Reset it did not have.

One implementation note worth keeping: the popover's outside-click handler closed
it before the page-level Apply's own click could fire, so the page button could
never reach the staged value. The staged selection now lives in the store, and
the outside-click handler ignores anything marked `data-keep-pop`.

### 8. Empty selections

Clearing every vendor falls back to all vendors; clearing every vertical empties
the page. Asymmetric, but deliberate: a vendor filter with nothing in it is
meaningless, while "no vertical in scope" is a real state. Controlled by
`emptyMeansAll` on the multiselect.

## Content

### 9. Headcount by Role total

Showed 75 for PH Engineering. The product shows 69, which is the sum of the
mapped role rows; 75 is the licensed headcount that appears as Total Headcount in
Vendor Profiles. The two are different numbers and the prototype conflated them.
Now derived from the role rows, with a test asserting the relationship.

### 10. Employee tiles carried a delta

Over Utilized Employee and Under Utilized Employee showed a period comparison.
Neither the prototype nor the product does. Removed.

### 11. Metric names

The live build has shipped the renames from the metric tooltip spec:
**Cost at Risk is now Cost Loss** and **Idle Cost is now Idle Time Cost**.
Adopted, in `config/copy.json` only. The metric ids are unchanged, so nothing in
the engine, the lens config or the tests had to move. The key-value row inside
the Idle Time Cost card follows the same label rather than repeating it.

### 12. Second vertical

The live filter bar now reads "Healthcare + 1 More". A second vertical is in
`config/verticals.json` so the control is demonstrably real. No vendors are
assigned to it yet, so selecting it alone gives the empty state. Assign vendors
by setting their `vertical` id when that data arrives.

### 13. Markup details

Risk Status conditions render on one line with a break, matching the prototype.
Key-value labels no longer emit a trailing space when they carry no tooltip.

## Deliberate differences from the live build

These are not defects. They are choices, and each has a reason.

| | Live build | This prototype | Why |
| --- | --- | --- | --- |
| Metric subtext | A descriptive paragraph under every metric title | Removed | The Sep 2026 metric tooltip spec removes it in favour of the info tooltip |
| Info tooltips | Every one reads "Planned vs actual" | The spec's per-metric copy | Same spec |
| KPI hero strip | Same four values on every period, identical on two different pages, all labelled "vs last quarter" | Recomputes with every filter | The live strip does not reconcile with the cards below it |
| Capacity Utilization | Prints hours that do not divide to the percentage beside them | Percentage and hours agree | Arithmetic |
| Metric chips | Gated behind Apply | Commit on click | Your earlier request |

## How the audit was run

The comparison harness is not shipped in the project, but the method is worth
repeating:

- Render both builds in Playwright, walk `.sect` and `.kpi`, and capture text
  plus chart geometry measured with `getBBox()` so a `<rect>` and a `<path>` are
  measured the same way.
- Diff the two captures per lens and period, grouping by what changed rather
  than by where, so 231 raw differences collapse into a dozen causes.
- Read the live product's chart configuration from the React fibre tree rather
  than from pixels: walk `__reactFiber$*` from each `[data-highcharts-chart]`
  container up to the props holding `options.series`.

After the fixes the remaining differences against the v1.0 prototype are exactly
the intended ones: the overlay geometry, the corrected axis ladder, the two
renames, and whitespace in the DOM text dump.
